# /review — 仕様と実装のズレを検出する

## 目的

実装が `spec/<機能名>.md` に書かれた機能仕様に沿っているか、**レビュー担当が検査する**。

> 単体版（1人のエージェントが全工程を担う版）ではこの工程を「自分で読み直して確認する」形で行っていましたが、SpecDrivenTeam では **別の担当（レビュー担当）が検査する** ことで、見落としを構造的に減らします。書いた本人が見直すより、別の目で確認する方が抜けに気づきやすいためです。

これは「ダメ出し」ではなく、**「ズレに早く気づいて直す」ための工程**。この伴走の姿勢は担当が変わっても変わりません。

## 手順

### 1. 伴走役がレビュー担当に委譲

実装完了後、伴走役が `spec/<機能名>.md` の該当抜粋と実装ファイル一覧を添えてレビュー担当に依頼する：

```
<機能名> のレビューを担当してください。

## 仕様（spec/<機能名>.md より抜粋）
{該当部分をそのまま貼る}

## 対象ファイル
{実装担当が変更・作成したファイル一覧}

## 手順の参照
skills/review/SKILL.md を読んで、その手順に従ってください。
```

### 2. レビュー担当が spec/<機能名>.md と README を読む

該当する機能ファイル（`spec/<機能名>.md`）の 機能仕様 / 受け入れ基準（AC）/ データモデル / 制約を整理する。
技術スタックやアーキテクチャに関わる実装なら、README（技術仕様）とも照らし合わせる。

### 3. レビュー担当が実装コードを読む

実装したファイル群を読み、以下を確認：

- **機能仕様** を全て満たしているか
- **受け入れ基準（AC-1, AC-2, ...）** を全て満たしているか
- **データモデル** が spec の通りか
- **非機能要件**（性能 / セキュリティ）を守っているか

### 4. ズレを検出

以下の5つの観点でズレ・問題を探す：

| 種類 | 内容 |
|---|---|
| **抜け** | spec にあるが実装にない（実装し忘れ） |
| **過剰** | 実装にあるが spec にない（書いてないものを作った） |
| **解釈ずれ** | 仕様の解釈と実装が違う |
| **副作用** | 既存挙動が壊れている（テスト失敗で検出される） |
| **安全** | 「安全の約束」（AGENTS.md）に反していないか。特に：①秘密情報がブラウザ側コード・リポジトリに入っていないか ②spec の「扱う大事なデータ」に ✅ がある機能で、認証・入力チェック・保存場所が仕様どおりか ③今回の変更で **初めて動き出す既存コード**（元からあったが呼ばれていなかった処理）があれば、それも動作確認の対象に含めているか ④**AI の出力をそのままコマンド実行・HTML 埋め込みしていないか**（**プロンプトインジェクション**（利用者の入力で AI の指示を乗っ取る攻撃）の入口になるため。`/secure` を通さない日常の小さな改修でも、AI の出力を扱うコードを触ったときは必ず確認する） |

> 5つ目の「安全」観点の補足：日々のレビューでは上記の4点だけを見ます（公開前のフルチェックは `/secure`＝安全チェック担当の担当）。③は「配線を繋いだら、繋いだ先も点検する」という発想です — 直した機能が、眠っていた別のコードを初めて動かすことがあるためです。④は AI を使う機能を触ったときだけ確認すれば十分です。

レビュー担当は **読み取り専用**（Read, Grep, Glob）のため、検査は今回触る範囲だけに絞る（パターン C の哲学: 既存コード全体への指摘はしない）。

### 5. レビュー担当からの報告

レビュー担当が伴走役にとって分かりやすい形で報告する：

```
## 仕様レビュー結果

### 仕様を満たしている箇所 ✅
- spec/system-prompt.md AC-1「リロード後も値が残る」
  → src/lib/storage.ts で対応 ✅
- spec/system-prompt.md AC-2「既定値に戻せる」
  → src/components/SettingsModal.tsx の resetButton で対応 ✅

### 気になる点
- spec/system-prompt.md AC-3「空文字入力時はエラー表示する」が、実装に見当たりませんでした
  → 修正の案：SettingsModal.tsx の保存ボタンに、空文字チェックを追加するのが良さそうです
  → これは私から提案する形ですが、ご相談させてください

### spec への追記をおすすめする点
- 実装中に出てきた「キャンセル時の挙動」が spec/system-prompt.md にまだ書かれていません
  → spec/system-prompt.md に「キャンセル時はパネルを閉じて値は保存しない」を追記しておくと、後から振り返るときに役立ちます

### テスト結果
- 12件 成功 / 0件 失敗 ✅
```

### 6. 伴走役が利用者に翻訳して報告

レビュー担当の生の報告文をそのまま貼らず、伴走役の一人称に翻訳して伝える（「レビュー担当から良い指摘が1つありました」等）。

### 7. 修正アクション（伴走役が利用者に判断を仰ぐ）

ズレが見つかった場合、レビュー担当は**修正できない**（読み取り専用）ため、伴走役が利用者に判断を仰ぐ：

- **実装側を直す** — 仕様が正しい → 実装担当に修正を依頼する
- **仕様側を直す** — 実装の方が正しい → `spec/<機能名>.md` を更新する（伴走役の仕事）
- **判断つかない** — 利用者に確認する

> 💡 **Antigravity では**: ズレの修正方針の決定には `ask_question` ツールを使い、「1. 実装を仕様に合わせる（推奨）」「2. 仕様を現在の実装に合わせる」などの選択肢モーダルを提示すると、市民開発者が迷わずワンクリックで判断できます。

```
ズレが見つかったとき、対応の選択肢は2つあります：
1. 仕様の方を実装に合わせる（実装が正しい場合）
2. 実装の方を仕様に合わせる（仕様が正しい場合）

今回は AC-3 が実装に無いケースなので、おそらく 2 の対応が必要かと思います。
進めてよろしいですか？
```

修正が必要な場合、伴走役は実装担当に差し戻し、修正後に再度レビュー担当へ検査を依頼する（※差し戻しの上限は 2 回まで）。

---

## 差し戻しの上限（2回まで）

> この上限の正本は agents/SDT-tech-lead/AGENTS.md「レビュー往復の上限」です。矛盾したら正本が勝ちます。

同じ機能についてのレビュー差し戻し（指摘 → 実装担当が修正 → 再検査）は、**2回まで**。

3回目に入りそうなときは修正を続けず、伴走役が利用者に状況を報告して判断を仰ぐ：

> 「レビューで2回直したのですが、まだ気になる点が残っています。ここまでの経緯を説明するので、一緒に方針を決めさせてください（仕様を見直すか、今の形でいったん進めるか）」

終わらないレビュー往復は品質ではなく疲労を生みます。完璧主義はこのチームの敵です。

---

## 報告のトーン

- ❌ 「実装に抜けがあります」「品質が低いです」
- ⭕ 「気になる点が1つあります」「ここを足すと完成度が上がります」

レビューは **粗探しではなく、品質を一緒に高める作業** であることを忘れない。担当が変わっても、この伴走の姿勢は共通です。

---

## 入力例

- 「実装終わったのでレビューして」
- 「spec/ の仕様と実装、ズレない？」

## 出力例

- 仕様レビュー結果（上記フォーマット）
- 修正提案（実装 or 仕様 のどちらをどう直すか、選択肢の形で提示）

---

## やらないこと

- 仕様にない観点で勝手にダメ出ししない（コードスタイル / 命名 / 設計など、依頼外の指摘はしない）
- ズレを見つけても**レビュー担当自身が修正しない**（読み取り専用。実装担当への差し戻しで対応する）
- 「だいたい合ってる」で終わらせない（具体的に対応関係を示す）
- 厳しい口調で指摘しない（伴走の姿勢を保つ）
- レビュー差し戻しを3回以上続けない（利用者に相談する）
- 専門用語を解説なしで使わない
