# /implement — GAS アプリの場合の追加ルール

> SKILL.md の手順（仕様の確認 → プランの提示 → 実装 → テスト → 引き継ぎ）はそのまま使う。GAS では「テスト実行」のあとに **保存（push）と確認用 URL での確認** が加わる。

## 役割分担（GAS のとき）

| 工程 | 担当 |
|---|---|
| プランの提示・利用者の OK | 伴走役（tech-lead） |
| `.gs`・`.html` の実装、テスト実行、保存（`clasp push`）、確認用 URL の取得（`clasp deployments`） | 実装担当（coder） |
| `clasp create`（Google ドライブにファイルを作る）の **利用者への確認** | 伴走役。OK が出たら実装担当に実行を委譲する |
| 確認用 URL と「目で確かめる AC」のチェックリストを利用者に渡し、結果を受け取る | 伴走役 |
| 確認用 URL で違いが見つかったときの修正 | 実装担当（伴走役が AC 番号と症状を添えて差し戻す） |

- 実装担当は `.clasp.json` が無い場合、`clasp create` を **自分の判断で実行しない**。「Google 側にファイルがまだ無い」と伴走役に報告して止まる
- 実装担当の完了報告には、テスト結果に加えて **push の結果と確認用 URL** を必ず含める
- 下の手順で「利用者に伝える・案内する」とある箇所は、伴走役が行う

## 実装の書き方

- **判定・計算・整形は、小さな関数に分けて `.gs` に書く**。`doGet` や、画面から呼ばれる関数（`google.script.run` の先）の中に直接書かない。分けておくと `/test` で自動テストできる
- **秘密情報は `PropertiesService.getScriptProperties().getProperty('GEMINI_API_KEY')` のように読む**。キーそのものをコードに書かない。スクリプトプロパティへの値の入力は、利用者が Apps Script の「プロジェクトの設定」で自分の手で行う（伴走役が手順を案内する）
- **画面へ返す値は JSON にできる形だけ**（文字列・数値・真偽値・配列・オブジェクト）。日付は `toISOString()` などで文字列にして返す（`Date` のままだと画面側で受け取れない）
- **画面へ返す値に、秘密情報やシート全体のデータを含めない**。画面に必要な項目だけを返す（画面側に届いた値は、ブラウザから誰でも見られるため）
- 画面側から呼ばれる関数でも、**入力チェックは `.gs` 側でもう一度行う**（画面のチェックだけでは素通りされることがあるため）

## テストのあと：保存（push）と確認用 URL（SKILL.md「4. テスト実行」に続けて行う）

### 1. 保存（push）の前の確認

- 差分に API キーらしき文字列が入っていないかを見る（「安全の約束」2）
- `.clasp.json` があるか確認する。**ない場合**（まだ Google 側にファイルが無い）は、利用者に「Google ドライブに Apps Script のファイルを作ってよいか」を確認してから作る：
  ```bash
  clasp create --type webapp --title "<アプリ名>"
  ```
  > 注意：このコマンドは `appsscript.json` を上書きすることがある。実行前に中身を控えておき、実行後に `timeZone`（`Asia/Tokyo`）と `webapp` の設定が元のままか確かめ、変わっていたら戻す

### 2. 保存（push）

```bash
clasp push
```

利用者には一言添える：

> 「PC のファイルを Google 側に送りました。Google 側（Apps Script のエディタ）で直接書き換えた内容があった場合は、今の送信で上書きされています。直すときは、いつもこちら（PC 側）で直しましょう」

### 3. 確認用 URL を案内する

確認用 URL は、保存した最新の内容がすぐ見られる、**作った本人だけが開ける URL**（末尾が `/dev`）。

```bash
clasp deployments
```

一覧の `@HEAD` の行にある ID を使い、`https://script.google.com/macros/s/<ID>/dev` を案内する。

- 初めて開くときは「権限の確認」画面が出る。何を許可しているか（スプレッドシート・外部への接続など）を先に説明し、**承認は利用者本人が行う**（チームの誰も代行できない）
- 「公開」（`clasp deploy`、末尾が `/exec` の URL を人に渡すこと）は `/implement` では行わない。公開の話が出たら `/secure` を通す

### 4. 確認用 URL で受け入れ基準を確かめる

spec の AC のうち、**「確かめ方: 確認用 URL」になっているものをチェックリストにして** 利用者に渡し、1 つずつ一緒に確かめる：

```
確認用 URL を開いて、次の 2 つを確かめてみてください：
- [ ] AC-1 締切を日付で入力できる（タスク追加の画面に日付の欄があり、選べる）
- [ ] AC-3 期限切れのタスクが赤で表示される（過去の日付で 1 件追加してみてください）

違っていたら、AC の番号を添えて教えてください。
```

- 自動テストが緑なのに画面が違う場合は、**判定の結果を画面に渡す部分**（`.gs` の戻り値、`.html` の表示処理）がずれていることが多い。そこから調べる

## 報告の仕方（SKILL.md の読み替え）

「動作確認の手順」は `npm run dev` ではなく、確認用 URL で書く：

```
## 動作確認の手順
1. 確認用 URL を開く：https://script.google.com/macros/s/<ID>/dev
2. タスク追加で、締切に昨日の日付を入れて追加する
3. 追加したタスクが赤で表示されることを確認する
```

## やらないこと（追加）

- 利用者の確認なしに `clasp create`（Google ドライブにファイルを作る）・`clasp deploy`（公開）をしない
- スクリプトプロパティの値を、チームの誰も読み出して表示しない
- Google 側のエディタで直接コードを書き換えない（PC 側が正本）
