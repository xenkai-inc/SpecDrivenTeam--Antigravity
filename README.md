# SpecDrivenTeam

スペック駆動開発で動く、**市民開発者** の伴走パートナー — の **チーム版**。

> 「エージェントに開発させる」から「**エージェントチームに開発させる**」へ。

- 配布版数: **v0.1.0**
- 単体版（SpecDrivenCoder）からの分岐元: commit `6b59d9c`

---

## これは何か

`SpecDrivenTeam` は、Antigravity 上で動く **開発エージェントチーム** です。

あなたの話し相手は単体版と同じく **伴走役 1 人**（tech-lead）ですが、その裏で専門の担当者たちが分業します：

```
あなた（利用者）
  ↕ 会話するのはこの 1 人だけ
[伴走役（tech-lead）] — 仕様づくり・依頼・確認・報告。コードは書かない
  ├─ [実装担当]         コードを書く
  ├─ [テスト担当]       テストを書く・実行する
  ├─ [レビュー担当]     仕様とのズレを検査する（読み取り専用）
  ├─ [安全チェック担当] 公開前の安全チェック（読み取り専用）
  └─ [デザイン担当]     UI の見た目の方針を決める
```

一番大事な違いは「**書く人と確認する人が別**」なこと。Antigravity では `define_subagent` の機能により、レビュー担当や安全チェック担当を**システムレベルで読み取り専用（コード改変不可）**に設定し、検査の独立性を確実に守ります。

## 単体版（SpecDrivenCoder）との関係

| | SpecDrivenCoder（単体版） | SpecDrivenTeam（このリポジトリ） |
|---|---|---|
| 構成 | 1 エージェントが全工程 | 伴走役 + 担当者 5 人の分業 |
| 使い方・フロー・報告 | 同一 | 同一（覚え直すことはありません） |
| 品質の守り方 | 自分で読み直す | **別の担当が検査する** |
| 位置づけ | 入門〜日常使い | 単体版 README「育て方 Step 5」の到達点 |

- **置き換えではなく併存**です。単体版で十分なら単体版を使い続けて構いません
- 共通部分（トーン・安全の約束・skills・templates）は **単体版が正本** で、このリポジトリへは手動で同期しています（対応表は下記）

## 使い方

### 初回セットアップ

```bash
git clone <このリポジトリのURL> ~/develop/SpecDrivenTeam
```

### 開発を始める

1. Antigravity を起動し、ワークスペースとしてこの `SpecDrivenTeam` ディレクトリを開きます。
2. `GEMINI.md` が自動ロードされ、伴走役（tech-lead）として立ち上がります。

### 依頼の出し方（単体版と同じ）

```
~/develop/MyChat にシステムプロンプト切替UI を追加してください。
```

パスを省略すると、伴走役が丁寧に確認してくれます。

## 動作の流れ

```
依頼
  ↓
① 対象プロジェクトの確認（新規 / 既存 / 既存だが仕様書なし）
  ↓
② README を最初に読む（なければ技術仕様つきで作成）
  ↓
③ /spec      — 仕様を書く・追記する（伴走役があなたと対話しながら）
  ↓
③.5 /design  — UI を持つ画面のときだけ：デザイン担当が方針を起草
  ↓
④ /test      — テスト担当がテストを書く（新仕様のテストは「赤」= 未完成の目印から始まる）
  ↓
⑤ /implement — 実装担当が実装し、テストが全て緑（成功）になるまで確認する
  ↓
⑥ /review    — レビュー担当が仕様と実装のズレを検査する（読み取り専用）
  ↓
⑥.5 /secure  — 公開・デプロイするときだけ：安全チェック担当が公開前チェック（読み取り専用）
  ↓
報告（できるようになったこと / 動作確認の手順を含む）
```

工程の名前も順番も単体版と同じです。変わったのは「誰がやるか」だけ。

## 構造

チームのメンバーは `agents/` 配下に 1 人 1 ディレクトリで並んでいます（誰がいるか一目で分かります）。

```
SpecDrivenTeam/
├── GEMINI.md              # Antigravity のエントリ（伴走役・サブエージェント連携ルール）
├── CUSTOM.md              # あなたのカスタマイズ置き場（本体更新と衝突しない）
├── .agents/               # Antigravity のカスタムディスカバリ規格
│   └── skills/            # skills/ から同期された実体コピー（symlink 不使用）
├── agents/                # チームメンバーの定義（★編集するならここ）
│   ├── SDT-tech-lead/AGENTS.md  # 伴走役（tech-lead）。トーンと安全の約束の正本
│   ├── coder/AGENTS.md    #   実装担当
│   ├── tester/AGENTS.md   #   テスト担当
│   ├── reviewer/AGENTS.md #   レビュー担当（読み取りのみ）
│   ├── security/AGENTS.md #   安全チェック担当（読み取りのみ）
│   └── designer/AGENTS.md #   デザイン担当
├── skills/                # 各工程の手順（spec / design / test / implement / review / secure）。各フォルダに GAS 用の gas.md
├── templates/             # README / 仕様 / テスト / pre-commit の雛形（GAS 用は templates/gas/）
└── scripts/
    ├── sync-agents.sh      # skills/ の内容を .agents/skills/ に同期する
    └── check-standalone.sh # このスターター自体の健全性チェック
```

**担当者の定義を編集したいとき**は `agents/<役割>/AGENTS.md` を直接修正してください。Antigravity では `agents/<役割>/AGENTS.md` の内容がそのままサブエージェントの定義として読み込まれます。なお、`skills/` 配下の工程手順を編集したときは、`bash scripts/sync-agents.sh` を実行して `.agents/skills/` に反映してください（`check-standalone.sh` が両者の一致を検査します）。

## よくある質問

### Q. 単体版と使い方は変わりますか？
A. 変わりません。話し相手は伴走役 1 人で、依頼の出し方・工程・報告の形も同じです。裏で担当が分かれて動くぶん、**応答に少し時間がかかる**ことがあります（伴走役が「いま実装担当が書いています」のように進捗を伝えます）。

### Q. 画面に英語のエージェント名や承認ダイアログが出ます。
A. Antigravity 本体の表示で、担当サブエージェントが動いているサインです。覚える必要はありません — 伴走役が日本語の役割名（実装担当・レビュー担当…）で説明します。承認を求められたら、内容を読んで OK するだけで大丈夫です。

### Q. モデル（頭脳）はどうなっていますか？
A. あなたが Antigravity で選んだメインのモデルを、チーム全員が引き継ぎます。追加費用の仕掛けはありません。慣れてきたら、担当ごとにモデルを変えることもできます（下記「設計の考え方」を参照）。

### Q. 自分の会社のルールを覚えさせたい。
A. **CUSTOM.md に追記してください**（AGENTS.md は直接書き換えない）。本体を将来更新しても、あなたの追記が消えません。

### Q. Google Apps Script（GAS）のアプリにも使えますか？
A. 使えます（単体版と同じ対応です）。対象プロジェクトに `appsscript.json` があれば伴走役が GAS アプリと判定し、担当への依頼文に各工程の `gas.md` を添えます。判定・計算はアプリのコードを書き換えずに PC で自動テストし、画面・保存・AI の返答は、実装担当が保存（push）したあと確認用 URL で一緒に確かめます。公開前には、安全チェック担当が公開範囲と実行ユーザーの組み合わせを点検します。

### Q. セキュリティが心配です。
A. 単体版と同じ「安全の約束」（API キーを晒さない・commit 前チェック・個人情報には認証を既定提案など）をチーム全員が守り、公開前には安全チェック担当が `/secure` で総点検します。あなたがチェックリストを覚える必要はありません。

## 設計の考え方（育てる前に読む）

このチームを育てる（担当や工程を足す）前に、崩さないでほしい設計の芯が 4 つあります。ここを守れば、育てても一貫性が保てます。

### 1. 2 つのレイヤ +「あなたのメモ帳」

このチームは **2 層 + 1 つのメモ帳**でできています。新しく何かを足すとき、置き場はこの表で決まります：

| 足したいもの | 置き場 | 意味 |
|---|---|---|
| 新しい担当 | `agents/<役割>/AGENTS.md` | **誰が・何に責任を持つか（WHO）** |
| 新しい工程・手順 | `skills/<工程>/SKILL.md` | **どうやるか（HOW）** |
| あなたの会社/プロジェクトの決まりごと | `CUSTOM.md` | **使って分かった学び・ルール** |

- 担当の定義（`agents/`）に手順を長々と書かないでください。手順は `skills/` に置いて、担当にそこを参照させます。両方に同じことを書くと、直すとき片方が古くなります
- 「使ってみて分かった決まりごと」は `CUSTOM.md` に足します。窓口役がそれを担当への依頼文に運びます
- 常設の開発チームでは「学びを溜める専用の置き場」を設けることがありますが、このチームには **あえて設けていません** — clone して個人が使う道具で、常設チームのようには縦に蓄積しないためです。**学んだルールは `CUSTOM.md`、汎用化した手順は `skills/`** の 2 本立てで足ります（もしこのチームを常設の自分専用チームとして多数の案件で回すようになったら、そのとき自分で置き場を足せば十分です）

### 2. 話し方の正本は 1 か所だけ

全員の話し方（伴走トーン）の正本は `agents/SDT-tech-lead/AGENTS.md` の「接し方の規則」です。各担当の定義にはトーンの要点だけを置き、末尾で「正本に従う」と宣言しています。担当を足すときも、**トーンをコピーせず、この 1 行宣言で正本を指すだけ**にしてください。コピーすると、正本を直したとき担当側が古いまま取り残されます。

### 3. 誰でもそのまま使える状態を保つ（環境に依存しない）

特定の個人名・会社名・あなたの PC 固有のパスを、ファイルに書かないでください。誰が clone してもそのまま動く状態を保つためです。これは `scripts/check-standalone.sh` が門番になっていて、環境依存の混入・担当定義と自動コピーのズレ・余計なリンクを機械的に見つけてくれます。**育てたあとに一度走らせる**習慣をつけると安心です。

### 4. 足すときに避けること

- **担当の定義に「手順（HOW）」を書き込まない**（→ `skills/` へ）
- **同じ役割の担当を二重に作らない**
- **検査役（レビュー担当・安全チェック担当）に書き込み権限を足さない** — 検査する人が自分で直し始めると、検査の独立性が失われます。「書く人と確認する人を分ける」がこのチームの品質の芯です

### 育てるときに使える仕掛け：担当ごとに頭脳（モデル）を変える

Antigravity では、サブエージェント呼び出し時（`invoke_subagent`）の `Model` 引数（`inherit` / `pro` / `flash` など）によって担当ごとに頭脳（モデル）を変えることができます。**特にレビュー担当・安全チェック担当に上位モデル（pro 等）を指定する**と、「書く人と確認する人を分ける」効果が最大化します — 実装した頭脳より賢い頭脳で検査できるためです（※ご利用のモデルプランに応じて選択可能です）。

担当（`agents/`）や工程（`skills/`）を育てたあとは、`bash scripts/check-standalone.sh` を一度走らせてください（上の「3.」の門番です）。
