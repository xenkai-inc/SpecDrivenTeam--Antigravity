# /review — GAS アプリの場合の追加ルール

> SKILL.md の 5 つの観点（抜け・過剰・解釈ずれ・副作用・安全）と報告のトーンはそのまま使う。ここに書いたことだけ、GAS 向けに足す。
> 検査はレビュー担当（読み取り専用）、委譲と翻訳報告は伴走役。伴走役は委譲文に、テスト結果と **確認用 URL で確かめた AC の結果** を添える（レビュー担当は画面を開けないため）。

## 「安全」観点の読み替え

日々のレビューでは、次の 3 点を見る（公開前の総点検は `/secure`）：

1. **秘密情報の置き場** — API キーが `.gs`・`.html` に直接書かれていないか。`PropertiesService.getScriptProperties()` から読んでいるか
2. **画面に返している値** — 画面から呼ばれる関数の戻り値に、秘密情報・他の人のデータ・シート全体のデータが含まれていないか（画面に届いた値はブラウザから誰でも見られる）
3. **初めて動き出すコード** — SKILL.md と同じ。今回の変更で初めて呼ばれる関数・初めて触るシートがあれば、それも確認の対象に含める

## 受け入れ基準の照合

AC を「確かめ方」で分けて報告する：

- **自動テストの AC** → 対応するテストがあり、緑かどうか
- **確認用 URL の AC** → 委譲文に添えられた、利用者と確かめた結果（確かめた / まだ）。まだのものがあれば、伴走役に再確認を勧める

報告の例：

```
### 仕様を満たしている箇所 ✅
- AC-2「期限切れと判定される」→ Code.gs の isOverdue で対応、テスト緑 ✅
- AC-3「期限切れは赤で表示」→ 確認用 URL で確かめ済み ✅

### 気になる点
- AC-1「締切を日付で入力できる」は、確認用 URL での確認がまだです
```

## 副作用の確認

- `npm run test` の結果に加え、**保存（push）したあとに確認用 URL で既存の主な操作が動くか** を、伴走役から利用者に 1 つだけ試してもらうよう勧める（自動テストが届かない画面・保存の部分は、ここでしか副作用に気づけないため）

## Google 側との食い違い

- 利用者が Google 側のエディタで直接書き換えた形跡（PC 側にない関数がある、など）を見つけたら、上書きを勧めず伴走役に報告する。伴走役は利用者に次のように確認する
  > 「Google 側にだけある変更があるようです。次の保存（push）で消えてしまうので、先に PC 側に取り込みますか？（`clasp pull` で取り込めます）」
