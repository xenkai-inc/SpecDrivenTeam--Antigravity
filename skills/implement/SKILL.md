# /implement — 仕様に沿って実装する

## 目的

`spec/<機能名>.md` に書かれた機能仕様と、README の技術仕様に沿ってコードを実装する。

> このスキルの実行主体は **実装担当（coder）** です。伴走役はプランの提示・利用者の OK 取得・委譲・完了報告の翻訳を担い、コードを書くのは実装担当です。**軽微な修正（typo 1文字でも）例外を設けず、必ず実装担当に委譲します** — 書く人と確認する人を分けることが、このチームの品質の守り方だからです。

## 前提

- 対象機能の `spec/<機能名>.md` が書かれている
- README（技術仕様）を読んで、技術スタック・全体構成を把握している
- 既存挙動を変える場合は、`/test` で safety net（セーフティネット：既存の動きを守るテスト）が用意されている

これらが揃っていない場合は、伴走役が `/spec` または `/test` を先に実行するよう、利用者に **理由を添えて** 提案する：

> 「実装に進む前に、まず仕様を書いておきましょう。書いたものを目印に進めると、後から『何を作ろうとしたか』が分からなくなるのを防げます」

---

## 手順

### 1. 仕様の確認（伴走役）

README（技術仕様）と対象機能の `spec/<機能名>.md` を読み直し、以下を明確にする：

- 技術スタック・既存の構成（README）— 既存の作りに合わせるため
- 機能仕様（何をするか）
- 受け入れ基準（AC-1, AC-2, ...）
- データモデル
- 非機能要件

**UI を持つ画面を実装する場合**は、`spec/design.md`（デザイン方針）も必ず読む。
まだ無ければ `/design` を先に通すよう、利用者に理由を添えて提案する：

> 「この画面はモダンな見た目に仕上げたいので、実装の前に色やレイアウトの方針を1回だけ決めておきましょう。後から見た目を直すより手戻りが少なく済みます」

実装後は、`/design` の **モダンUIチェックリスト**（SVGアイコン / cursor-pointer / hover / コントラスト …）で仕上がりを確認する。

### 2. 変更内容のプランを提示（伴走役）

実装担当に委譲する前に、**どのファイルをどう変えるか** を伴走役が利用者に伝えてから進める：

> 💡 **Antigravity では**: 変更規模が大きい場合は、Planning Mode に従い `implementation_plan.md` などの Artifact を活用して右側ペインに見やすく提示します。また、「進めてよろしいですか？」の確認には `ask_question` ツールを使うと市民開発者がスムーズに OK を出せます。ファイルパスは `[ファイル名](file:///絶対パス)` 形式でクリック可能にします。

```
spec/system-prompt.md「システムプロンプト切替UI」を実装します。
以下のファイルを変更する予定です：

- src/components/SettingsModal.tsx（新規作成）
  → 設定パネルのUIコンポーネント

- src/lib/storage.ts（既存ファイルに関数追加）
  → ブラウザに設定を保存・読み出しする関数

- src/app/page.tsx（既存ファイルを少し変更）
  → SettingsModal をページに表示する

ここからは実装担当にコードを書いてもらいます。書き上がったら私が中身を確認してから報告しますね（数分かかることがあります）。
進めてよろしいですか？
```

利用者の OK を待ってから実装担当に委譲する。自明な小変更（typo 修正など）でも、伴走役が「1文字の修正でも実装担当にお願いしますね — 書く人と確認する人を分けるのが、このチームの品質の守り方だからです」と理由を添えて委譲する（プラン提示自体は簡略化してよい）。

### 3. 実装担当への委譲

委譲文テンプレート（詳細は AGENTS.md「委譲の作法」を参照）：

```
<機能名> の実装を担当してください。

## 仕様（spec/<機能名>.md より抜粋）
{該当部分をそのまま貼る}

## お願いする成果物
{作成・変更するファイル。プランで提示した内容}

## 完了の条件
{テストが緑・など検証可能な形で}

## 手順の参照
skills/implement/SKILL.md を読んで、その手順に従ってください。

## 守ってほしいこと
- commit はしないでください（テスト確認後に私が行います）
- 依頼範囲外の "ついで" 修正をしない：気づいたことがあれば最後に別途報告してください
- 変更は working tree に残したまま、変更ファイル一覧と結果を報告してください
```

### 4. 実装担当が行う実装

仕様の受け入れ基準（AC）に対応するコードを書く：

- **既存ファイル** を変更する場合：変更前後の差分を明示
- **新規ファイル** を作る場合：作成意図を一言添える
- **依頼範囲外の "ついで" 修正をしない**：気づいたことがあれば最後に別途報告

### 5. テスト実行（実装担当）

実装後、必ずテストを実行：

```bash
npm run test
```

実行結果を伴走役に報告する：

- **全部緑（成功）** → 伴走役が利用者に「テストが全て成功しました」と伝えて次に進む
- **失敗あり** → 慌てず内容を一緒に読み解き、テストと実装のどちらが正しいかを利用者と相談する（実装担当・伴走役ともに勝手に判断しない）

### 6. 引き継ぎ（伴走役）

実装完了後は `/review`（レビュー担当への委譲）を実行：

- 仕様と実装にズレがないかを最終確認
- 報告フォーマットで利用者に返す

---

## 報告の仕方（伴走役が利用者に返す）

完了したら、利用者にとって「何ができるようになったか」が分かるよう報告する：

```
✅ 完了：システムプロンプト切替UI の追加

## できるようになったこと
設定画面でシステムプロンプトを変更し、保存できるようになりました。
保存した内容はブラウザを閉じても残ります。

## 変更したファイル
- spec/system-prompt.md（新規追加）
- src/components/SettingsModal.tsx（新規）
- src/lib/storage.ts（関数 saveSystemPrompt / loadSystemPrompt を追加）
- src/app/page.tsx（SettingsModal を表示）

## テスト結果
- 5件 成功 / 0件 失敗 ✅

## 仕様との整合
- spec/system-prompt.md AC-1, AC-2, AC-3 すべて満たしています（レビュー担当の確認も通っています）

## 動作確認の手順
1. アプリを起動する（npm run dev）
2. 右上の設定アイコンをクリック
3. テキストエリアにプロンプトを入力 → 保存ボタン
4. ページをリロード → 入力した内容が残っていることを確認
```

生の実装担当の報告文をそのまま貼らず、伴走役の一人称に翻訳する。

---

## 入力例

- 「spec/system-prompt.md を実装して」
- 「`/spec` で追加した機能、実装お願いします」

## 出力例

- 変更ファイルの一覧と差分
- テスト実行結果
- 利用者向けの完了報告（上記フォーマット）

---

## やらないこと

- `spec/<機能名>.md` に書かれていない仕様を実装しない
- 「ついでに」関係ない箇所をリファクタしない
- テストを実行せずに完了報告しない
- 利用者の承認なしに大きな構造変更（ファイル分割、ライブラリ追加など）をしない
- 失敗を厳しい口調で報告しない（伴走の姿勢を保つ）
- **伴走役自身がコードを書かない**（1文字の修正でも実装担当に委譲する。例外なし）
